# Secrets and credentials

Machines generate and hold secrets; the platform owner holds the few keys that
can recover or re-mint everything. Only secrets whose loss would destroy data
are escrowed; anything else is recovered by rotating it. The owner is never
locked out. Which tokens exist, where the escrow is kept and which keys can
open it are recorded in the private operations docs, not here.

## CRED-1 — nobody is locked out

The platform owner always has a break-glass path — a by-hand route for
emergencies — to every resource they own, and it works with CI down.

**Why:** automation that can lock out its owner turns one outage into two.

**Check plan:** the escrow drill (`CRED-6`) proves the recovery half; review of
any change to an access path.

## CRED-2 — generated secrets are never seen

A secret that can be generated is generated by CI, through the infrastructure
code, and never seen by a person. The deploy writes it to its host.

**Why:** copy and paste is where secrets leak and where the owner's time goes.

**Check plan:** review of each new secret in the diff and where its value comes
from.

## CRED-3 — only data-protecting secrets are escrowed, by CI

Only secrets whose loss would destroy data — infrastructure state passphrases,
backup encryption keys — are escrowed. CI escrows each one when it creates or
rotates it: it encrypts the value to the owner's escrow keys, a
hardware-backed daily key and an offline paper key, and stores the ciphertext
in a private off-site bucket.

**Why:** anything else is recovered faster and more safely by rotating it.

**Check plan:** a check that every job creating or rotating a data-protecting
secret runs the escrow step.

## CRED-4 — every generated secret rotates

Every generated secret has a scheduled rotation that waits only for the
approval click.

**Why:** a rotation with manual steps doesn't happen.

**Check plan:** a script comparing the secrets declared in infrastructure code
with the rotation workflows.

## CRED-5 — supplier tokens are narrow and re-minted yearly

A supplier token that no API can create is split per supplier project,
narrowed by policy where the supplier allows it, and re-minted every year from
an automatically filed issue.

**Why:** such tokens never expire and cover a whole project, so their scope
and their age are the only levers we have.

**Check plan:** a scheduled workflow that files the yearly re-mint issue.

## CRED-6 — the escrow is drilled

CI files a recurring drill issue: decrypt a test secret with each escrow key.
The drill runs monthly if it is inexpensive, and at least twice a year.

**Why:** an escrow nobody has opened hasn't been proven to work.

**Check plan:** the scheduled drill workflow and its closed drill issues.

## CRED-7 — CI credentials sit behind the approval

CI credentials are secrets on the protected deploy environment, never
repository-wide secrets.

**Why:** a secret a job can read without the approval click bypasses the only
human gate.

**Check plan:** an audit of each repo's repository-level secrets through the
GitHub API, failing on any deploy credential.

## CRED-8 — break-glass keys are hardware-backed

The platform owner's SSH key and two-factor logins are hardware-backed: the
private key never sits in a file on disk.

**Why:** a key file on a laptop can be copied without anyone noticing, and a
hardware-backed key can't.

**Check plan:** review of the access inventory in the operations docs.

## CRED-9 — the password manager holds personal logins only

The password manager holds the platform owner's personal logins only. No
machine secret lives in it.

**Why:** one browser extension holding every secret in the estate is a single
point of compromise.

**Check plan:** review of the password manager's contents during each escrow
drill.

## CRED-10 — secrets are read from files

A service reads its secrets from mounted files (the `*_FILE` convention)
rather than plain environment variables, wherever the application supports
it.

**Why:** environment variables leak into logs, crash reports and container
inspection.

**Check plan:** a check over Compose files for secret-like environment
variables that don't use `_FILE`.

## CRED-11 — gitleaks everywhere

gitleaks runs in pre-commit and in CI in every repo, and any finding fails.

**Why:** a secret caught before the push is a non-event; one caught after it
is an incident.

**Check plan:** the reusable scan workflow, and the gitleaks hook in the shared
pre-commit template.

## Direction

Later, and optionally: CI deploys use ten-minute SSH certificates, issued by a
small signer on our own hosts after it checks the job's GitHub identity. That
would give short-lived deploy credentials even where a supplier offers no
federated login.
