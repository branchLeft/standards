# Observability and alerting

Self-hosted Prometheus and Grafana give one view of system health; degradation is caught early by email, and only downtime and a short list of critical conditions page, at any hour. Which services count as core and where the monitoring runs is recorded in the private operations docs.

## OBS-1 — rate, errors and duration per endpoint

Every service exposes request rate, errors (by HTTP status code) and request duration per endpoint as metrics, from shared middleware.

**Why:** these three numbers show a service degrading before it fails.

**Check:** a test of the shared metrics middleware; a scrape check inside the CI smoke test (`CON-14`).

## OBS-2 — what pages

Only these page: downtime of a core service; critical host health (CPU or memory above 95% or disk above 90%); a failed deploy rollback; a missed monitoring heartbeat; log storage above 90% full; everything else goes by email or becomes an issue, and an error or exception never pages on its own.

**Why:** a page that is not urgent teaches its reader to ignore pages.

**Check:** promtool unit tests that exactly these rules carry the page label and no other rule does.

## OBS-3 — how a page arrives

A page goes to a phone push app and to email at the same time, at any hour, with push through a self-hosted ntfy that Alertmanager posts to directly.

**Why:** two channels mean one outage cannot silence a page.

**Check:** `amtool config routes test` cases for each paging rule's receivers.

## OBS-4 — alert email leaves the estate

Alert email goes to at least one mailbox hosted outside the estate.

**Why:** a mail server that is down cannot deliver the email saying so.

**Check:** review of the alert receiver list.

## OBS-5 — the monitoring is watched from outside

The monitoring is watched from outside the estate by a heartbeat, and a missed heartbeat pages.

**Why:** monitoring that dies silently looks exactly like "all clear".

**Check:** a promtool test that the always-firing heartbeat rule exists and routes to the external receiver.

## OBS-6 — one alert engine

Prometheus with Alertmanager is the only alert engine, and Grafana's own alerting stays off.

**Why:** two engines mean two sets of rules to test and two places to look.

**Check:** a CI check that Grafana's configuration disables its alerting.

## OBS-7 — dashboards and alerts are code

Dashboards and alert rules live in the repo and CI loads them, and nothing is edited in the Grafana web UI.

**Why:** a rebuilt Grafana comes back identical and every change is reviewed.

**Check:** a CI check that dashboard provisioning sets `allowUiUpdates: false`.

## OBS-8 — every alert is tested and says what to do

Every alert rule has a promtool unit test and a one-line "what to do" note linking to the operations docs.

**Why:** an alert with no next step is noise, and an untested rule may never fire.

**Check:** a script pairing every alert rule with a promtool test case and a non-empty action annotation.

## OBS-9 — metric retention

Raw metrics are kept 30 days, and aggregate series (recording rules and counts derived from logs) are kept 2 years in a second, small Prometheus instance, because each instance has a single retention setting.

**Why:** aggregates are cheap enough to keep for trends, while raw series only serve recent debugging.

**Check:** a CI check of each Prometheus instance's retention flag.

## OBS-10 — monitoring storage has its own alerts

Log and metric storage alerts by email when over 70% full, when recent growth would fill it within 7 days, when a host stops sending logs and when retention deletes fail, and pages at 90% full (`OBS-2`).

**Why:** losing logs means losing the ability to debug anything in the estate.

**Check:** promtool unit tests for each storage rule.

## OBS-11 — degradation is caught early

Gradual degradation (rising error rates, resource trends, certificates nearing expiry) alerts by email before it becomes downtime.

**Why:** early warning is what keeps incidents rare.

**Check:** promtool unit tests for the degradation rules; every scraped service has an error-rate rule.

## OBS-12 — Grafana access

Grafana is reachable in a browser through the edge at its own hostname over TLS using only its own login, with sign-up off, anonymous access off and brute-force protection on per user and per IP address.

**Why:** a browser view needs no tunnel, uses the one front door and does not depend on the identity service it helps to monitor.

**Check:** a CI check of Grafana's configuration for each of these settings.

## OBS-13 — named accounts

Each person gets a named Grafana account, and the bootstrap admin password is generated by CI (`CRED-2`) and not escrowed (`CRED-3`), so if lost it is reset on the host through the break-glass route.

**Why:** no admin password is copied by hand and every action is attributable to someone.

**Check:** review of the Grafana provisioning code.
